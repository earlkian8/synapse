SYNAPSE — Testing & Understanding Guide

A walkthrough for testing the system by hand, written in plain language. You do not need to know Laravel, React or machine learning to follow it.

Two parts of this guide go deeper than the rest: Part 3 (Performance Management) and Part 4 (Predictive Analytics). Those are the parts where the system is doing something you cannot check by eye, so they explain the arithmetic and how to read what comes out — not just which buttons to press.

Step 1 — check the database is running.

pg_isready

If it is not running, start it the way you normally do (sudo systemctl start postgresql).

Step 2 — load the demo data. Do this once. It wipes the database and fills it with a realistic sample company. Takes 30–60 seconds.

cd server
php artisan migrate:fresh --seed

You end up with two companies (SYNAPSE Demo Co and SYNAPSE Labs), 50 employees, job postings and applicants, about six weeks of clock-in history, plus leave, appraisals, trainings, awards, events and exits.

Step 3 — start the web app. One command starts the web server, the background job runner and the page builder. Leave the terminal open.

cd server
composer dev

Then open http://localhost:8000.

If composer dev fails, run the three pieces in separate terminals instead: php artisan serve, php artisan queue:listen --tries=1, and npm run dev.

Part 3 — Performance Management

This is the module most worth understanding properly, because it produces a single number that decides things about people — and that number is not a simple average.

3.1 What the module is for, in one paragraph

Every company appraises staff differently: different things measured, measured on different scales, weighted differently, and reported in the company's own words ("Outstanding", "Meets Expectations") rather than a universal 1–5. SYNAPSE lets each company define its own appraisal form — the framework — and then scores every appraisal against whichever framework it was opened under. Two employees on two different frameworks both end up with a comparable attainment percentage, even though nothing about their forms matched.

3.2 The four building blocks

Everything in this module is one of four things. Learn these and the rest follows.

BlockDecidesExample
Rating scaleHow something is measured "1–5 numeric", or "0–100 %", or named levels like Needs work / Solid / Exceptional
CriterionWhat can be measured "Quality of Work", using the 1–5 scale, default weight 2
FrameworkWho is reviewed, on which weighted sections and criteria "Support Team Appraisal" — applies to the Customer Support department
Rating modelThe words the result is reported in 90+ = Outstanding, 75+ = Exceeds, 60+ = Meets, below = Needs Improvement
Which framework applies to whom? A framework carries an eligibility rule — everyone, a department, a position, or an employment type. When HR opens an appraisal, the system picks the narrowest match: position beats department beats employment type beats everyone, with the company default breaking ties. It is only a suggestion — HR can always choose a different one.

3.5 Score an appraisal

Open one. Rate each criterion. Use exactly these scores so you can check the maths in 3.6:

SectionCriterionScore (1–5)
DeliveryQuality of Work4
Reliability5
BehaviourCustomer Communication4
Initiative3

Watch the result move as you type. A draft carries a live running result, because only the criteria you have actually rated are counted — an unrated section is left out entirely rather than dragged to zero.

Then: Submit (locks it once every criterion is rated) → Sign off → Acknowledge. An acknowledged appraisal is final.

3.6 How the number is actually calculated

This is the part worth reading twice. The result is not the average of 4, 5, 4, 3. It is computed in two levels, because that is how appraisal forms are written.

Level 1 — each score becomes a position on its own scale

A raw score means nothing until you know the scale it sits on. A 4 out of 5 and a 4 out of 10 are different achievements. So each score is first converted to a fraction between 0 and 1:

position = (score − scale minimum) ÷ (scale maximum − scale minimum)
CriterionScoreWorkingPosition
Quality of Work4(4 − 1) ÷ (5 − 1)0.75
Reliability5(5 − 1) ÷ (5 − 1)1.00
Customer Communication4(4 − 1) ÷ (5 − 1)0.75
Initiative3(3 − 1) ÷ (5 − 1)0.50

Level 2a — criteria are weighted inside their own section

section attainment = Σ(position × criterion weight) ÷ Σ(criterion weight)
SectionWorkingAttainment
Delivery(0.75 × 2 + 1.00 × 1) ÷ (2 + 1) = 2.50 ÷ 383.33%
Behaviour(0.75 × 1 + 0.50 × 1) ÷ (1 + 1) = 1.25 ÷ 262.50%

Level 2b — sections are weighted against each other

overall = Σ(section attainment × section weight) ÷ Σ(section weight)
overall = (83.33 × 60 + 62.50 × 40) ÷ (60 + 40) = 7500 ÷ 100 = 75.0%

Note that the plain average of 4, 5, 4, 3 is 4.0 out of 5, which is 75% — the same here only by coincidence of the weights. Change Quality of Work to weight 3 and the two answers part company. Check this on screen: the appraisal should read 75%.

The two numbers the system keeps

NumberWhat it isWhy it exists
Attainment %
(0–100)		The canonical result. 75.0 in our example. It is what the rating model bands are read from, and the only figure that compares fairly across different frameworks.
Overall score
(1–5)		The same figure stretched onto 1–5:
1 + (75 ÷ 100) × 4 = 4.00		 The forecast model, the promotion pipeline and the awards nominator were all built on a 1–5 number. Keeping it means those keep working.

Reading the band

75.0% is read against your rating model top-down — the first band whose "From" is at or below 75. Outstanding needs 90, so no. Exceeds Expectations needs 75 — yes. The appraisal reports Exceeds Expectations.

Try this to prove it to yourself: change Initiative from 3 to 4. Behaviour becomes (0.75 + 0.75) ÷ 2 = 75%, and the overall becomes (83.33 × 60 + 75 × 40) ÷ 100 = 80.0% — still "Exceeds Expectations", but you can watch it move.

3.7 Reading the cycle overview

The /performance landing page is about the cycle, not the person. Four things worth understanding:

What you seeWhat it meansWhat to do about it
CoverageHow many active staff have an appraisal in this cycle Below 100% means people were missed when the cycle was launched
Awaiting sign-offScored and submitted, but nobody has approved it This is the queue managers need to clear
Result spreadHow many people landed in each of your own bands If almost everyone is in one band, your bands are not discriminating
Per-department calibrationEach department's average as a deviation from the company average A department consistently +15 is usually a lenient reviewer, not better staff

3.8 Why an old appraisal never changes

When an appraisal is opened it freezes the framework it was opened under — the name, the sections, their weights, every criterion's own weight and its full rating scale, and the rating model. Retuning a framework, retiring a criterion or changing a scale therefore changes the next appraisal and never a past one.

Test it: score and submit an appraisal, then go back to /setup/kpi and change the Delivery section's weight from 60 to 80. Re-open the submitted appraisal — the result must be unchanged. Now launch a new cycle: the new appraisals use 80.

Part 4 — Predictive Analytics

Three pages sit under Analytics & AI. They look alike and are not alike. Understanding the difference is the single most important thing in this guide.

4.1 The three surfaces at a glance

SurfacePredictsBehind itIs it real?
Promotion ReadinessHow ready each person is for promotion (0–100) A trained Logistic Regression model, served by the Python service Real model, trained on a general public workforce dataset
Performance ForecastEach person's next-period rating (0–100) A trained Gradient Boosting model, same service Real model, same general dataset
Attrition RiskWho might leave Nothing. Numbers are invented in your browser. Demonstration only — the page says so itself
The honest headline. The two real models were trained on a general public workforce dataset, not on this company's history. (One of its columns is an Indian metropolitan classification — it is plainly not Philippine data.) They are demonstrating that the pipeline works end to end. The system says this on every page and refuses to retrain until it has enough of your own data — that mechanism is Part 4.6, and it is the most interesting thing here.

4.2 Promotion Readiness — how to read it

Go to Analytics & AI → Promotion Readiness and click Run assessment. Every active employee is scored in one batch.

What you get

ThingWhat it is
Readiness score0–100. It is the model's probability that this person is promotion-ready, multiplied by 100. A score of 72 means the model puts them at 72% probability.
TierThe score bucketed. The cut-offs are fixed:
TierScore range
Lowbelow 33
Medium33 to below 66
High66 and above

The factor bars — the useful part

Click an employee. You get diverging bars: green pushes toward readiness, red pulls away. These are not decoration and not guesses — they are the model's own arithmetic. For each input, the model multiplies the person's value by the weight it learned, and the bars show the six largest of those products.

So a long red bar on "Years since last promotion" means precisely: this person's time since last promotion is, in this model's arithmetic, the biggest single thing holding their score down. That is an actionable sentence a manager can use.

Protected attributes are never shown as factors — gender, marital status, age, education level and city tier are excluded from the explanation, and the HR system never sends them in the first place.

What the score is built from

Only data the HR system actually holds: tenure (date hired, last promotion), performance history (the latest scored appraisals — this is where Part 3 feeds in), certifications, salary and employment type. Anything else the model expects is filled in by its own averages.

4.3 Performance Forecast — how to read it

Analytics & AI → Performance Forecast → Run forecast. It predicts each person's rating in the next review cycle that is not yet closed.

ThingWhat it is
Predicted rating0–100, on the same attainment scale Part 3 produces
BandExceeds = 80 and above · On track = 60 to below 80 · Below = under 60
MovementThe predicted rating compared with the person's last actual cycle
Trajectory chartTheir past actual ratings as a solid line, then the forecast as a dashed point

Confidence does not mean what you think it means

Read this carefully. "Confidence" here is not the model's certainty. It is a data-completeness score: the share of the ten key inputs that were actually found in that employee's records, rather than filled in with an average.

Confidence 100% = all ten were real. Confidence 40% = six were guessed.

So low confidence means "we do not know much about this person", not "the model is unsure". The fix is data entry, not a better model.

The ten inputs counted are: performance last year, performance two years ago, manager rating, KPI achievement, years at company, years since last promotion, certifications count, salary, employment type, department.

Why this page has no factor bars

You will notice Promotion Readiness explains why and Performance Forecast does not. That is not an oversight. Promotion Readiness uses a linear model, which has one weight per input — so a per-person breakdown falls straight out of the arithmetic. The forecast uses gradient boosting, which is hundreds of small decision trees and has no such weights. The system returns nothing rather than inventing an explanation.

4.4 When the prediction service is off

Stop the Python service and reload either page. Expect: the page still loads, existing results still show, the Run button is disabled, and a banner reads roughly "Assessments are temporarily unavailable… try again shortly, or contact your system administrator." You should not see a stack trace, a status code, a model name, or an instruction to run a terminal command. That is deliberate — this is an HR screen.

4.5 Attrition Risk — the honest demo

This page generates its numbers in your browser. There is no model, no dataset and no notebook behind it, and nothing is saved to the database. It exists to show the shape of the surface. Its own provenance panel marks it provisional and explains why.

Because its runs live in browser storage, re-seeding the database will not clear them. To clear: developer tools → Application → Local Storage → delete synapse:attrition-risk:runs.

4.6 Model Graduation — the gate

This is the most distinctive idea in the system. Read this section even if you skip everything else in Part 4.

Under the header of each of the three pages sits a "Where these scores come from" panel. Collapsed, it is one line plus a stage badge and an n of m met count. Expanded, it shows a three-stage lifecycle with the retraining gate drawn closed.

StageMeans
ProvisionalRunning on a borrowed model. Your own outcome data is not yet being linked back.
CollectingStill on the borrowed model, but every score is now being matched against what actually happened. Time spent here counts.
GraduatedEnough of your own history exists to train a model on your workforce. The gate opens.

Each surface has its own requirements, because they learn from different things:

Promotion ReadinessPerformance ForecastAttrition Risk
Learns fromwho was promotedthis cycle's rating vs the lastwho left
Headline requirement120 promotions on record200 cycle-to-cycle comparisons80 departures on record
Its distinctive oneBalance between promoted and not-promoted — a model shown only successes learns nothing30 people with three or more appraisals — two points cannot show a trajectoryEvery departure carrying a reason: a resignation and a redundancy are opposite events
Current stageCollectingCollectingProvisional
Why Attrition is the odd one out. Its scores are generated in the browser and never stored, so the link between prediction and outcome sits at zero. Waiting does not move that requirement — which is exactly why it reads provisional where the other two read collecting. The panel is telling the truth about its own weakest surface.

How to read the requirement ledger

Each row is one requirement with a progress figure like 18 / 120. Click a row and it opens a drill-down explaining why that threshold — usually a rule of thumb like 10–20 recorded outcomes per input the model uses. Below the ledger, the panel also lists every input the score uses, grouped three ways:

StateMeaningWhat you would do
Used nowRead from your records and fed into every scoreNothing — keep the data clean
Recorded, not usedThe system already holds it; wiring it in needs no new data entryA development task, not a data task
Not recorded anywhereNo module produces itWould need a new field or module first

4.7 "Can I trust these numbers?" — the answer to give

If someone asks this in a demo or a defence, the correct answer is not "yes" and not "no". It is:

"Not yet as predictions about this workforce — and the system says so itself rather than hiding it. What is proven today is the full pipeline: real HR data mapped to a feature space, scored by a trained model, explained per person without touching protected attributes, and persisted with an audit snapshot. What is deliberately withheld is the claim that the numbers describe this company. The graduation gate names exactly what is missing, how far along it is, and refuses to retrain until it is there."

That is a stronger position than a confident number would be, and it is checkable — everything in it is on screen.

Part 6 — Known gaps

These are meant to be missing. Finding them is not finding a bug.

GapDetail

Part 7 — Starting over

If you break something, or want a clean demo again:

cd server
php artisan migrate:fresh --seed

This wipes everything and rebuilds the demo company. Your login does not change.

One exception: Attrition Risk runs live in browser storage, so re-seeding will not clear them — delete synapse:attrition-risk:runs from Local Storage as described in 4.5.
